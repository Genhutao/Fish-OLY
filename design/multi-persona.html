OLY World Engine / Multi-Persona & Presence

一个用户，多个角色，同一段时间

当前服务端是一个实时推进的单一世界。要支持「用户 X 名下有 a、b 两个角色，每天各自正常生活，且串门时两人必须同时在场」，需要把归属、日程、在场三件事从隐式变成显式。这份稿子只给设计，不含实现。

01

结论先说

不改「实时模拟」这个前提，只在它上面加三层：归属层、日程层、在场层。

归属从隐式变显式

一切数据以 user_id 为第一分区键。一个用户拥有一个世界、若干角色、若干场景；调度器按用户隔离，不共享 tick。

「每天模拟」= 每日计划 + 实时执行

不是每天跑一次批处理，而是每天生成一张日程表，再由实时时钟逐分钟执行。用户不在线，世界照样走。

交集发生在计划期，不是执行期

串门必须在计划阶段就和对方对表，落到同一段时间窗；执行期只做「按窗相遇」。否则一定出现「A 去了，B 不在」。

在场用租约表达

任何角色在同一 tick 只能属于一个会话。串门是一次多参与者会话，参与者必须同时拿到租约；拿不到就降级为「未遇」。

一句话架构：User →（DayPlan → Intent）→（Intersection → Session）→（Presence Lease）→ Events → Memory。串门不是一次 API 调用，而是一段**有起止时间、有参与者、有共享场景**的会话。
02

归属结构

世界属于用户，角色属于世界，场景是世界内的公共资源。角色之间不是「互相调用」，而是「共享一段场景与时间」。

五层对象

对象是什么关键点
User 用户隔离与计费的单位拥有一个世界；配额、时区、模型预算都挂在这里
Persona 角色可自主行动的人设实例属于某个 user；有独立的状态、记忆库、日程
Scene 场景世界内的公共场所有容量与可见性；是角色相遇的唯一空间
Session 会话一段有参与者的时间窗solo / pair / group；串门就是 pair 会话
Event 事件会话内的每一次变化记忆、审计、回放的唯一原料
03

数据模型

所有业务表第一列都是 user_id。会话与在场是这个模型新增的两张核心表。

表关键字段说明
usersid, tz, day_start, quota_jsonday_start 默认本地 04:00；配额含角色数、模型调用数
personasid, user_id, name, anchor, state_jsonstate 含 energy / mood / scene_id / agenda
scenesid, user_id, name, capacity, visibility容量用于限制同时在场人数
day_plansid, user_id, persona_id, day, seed, status一人一天一张；seed 保证可重放
intentsid, plan_id, persona_id, kind, scene_id, start_tick, end_tick, target_persona_id日程的最小单位；串门是 kind=visit 且带 target
sessionsid, user_id, day, scene_id, kind, start_tick, end_tick, statuskind ∈ solo / pair / group；一组 intent 折叠而来
session_participantssession_id, persona_id, role, join_tick, leave_tickrole ∈ host / guest；访客与主人在记忆里措辞不同
presence_leasesuser_id, persona_id, session_id, start_tick, end_tick唯一约束：同一 persona 的时间区间不得重叠
eventsid, user_id, day, tick, session_id, actor, type, payload幂等键 (session_id, tick, actor, seq)
memoriespersona_id, slot, member, refs[]refs 指向 event/session；写入只进本人记忆库
为什么在场要单独建表：「谁在什么时候在哪个场景」是串门能不能发生的事实依据。把它塞进 persona.state 会立刻变成并发写冲突；单独一张租约表，才能用一条唯一约束把「同一 tick 两个会话」这种错误挡在数据库层。
04

时钟与调度

「每天模拟」不是批处理，是「一天一张计划表 + 按真实时间逐分钟执行」。用户离线，世界照走。

时钟口径

概念取值说明
tick1 分钟一天 1440 tick；所有 intent / session 都用 tick 表达
日界本地 04:00避开午夜在线高峰，也让「熬夜」落在同一天
推进每 10 秒对齐一次算出应到 tick，补齐差值；不是每条消息一个定时器
会话粒度15 分钟的倍数串门常见 30–90 分钟；过短没有叙事价值

三层调度

01 计划日界生成每个角色 6–10 段 intent；种子 = H(user, persona, day)
02 交集同场景且时间重叠 ≥ 20 分钟 → 折叠成 pair 会话；串门先对表
03 执行按 tick 推进会话；solo 走模板，pair 才允许调模型
04 提交结束写摘要事件，两端各自写记忆，更新关系边

每个用户一个调度协程（或一个按 user 分片的 worker），同一用户的计划、交集、执行全部串行；不同用户之间完全并行。这样既不需要跨用户锁，也保证同用户内「先排计划、再定交集、最后执行」的顺序不会被并发打乱。

与现在的差别：当前是一个全局 tick 推进所有人。改造后 tick 仍然存在，但它是**每个用户自己的时钟**——用户 A 的世界走到 20:40，不影响用户 B 走到几点；跨用户的唯一交互是异步访客协议，不进实时会话。
05

交集与串门

核心问题：怎么保证「a 去找 b 的时候，b 真的在」。答案是把相遇从执行期提前到计划期，并给执行期留一个受控的兜底。

串门协议（同用户内）

步骤做什么失败时
1 声明a 的计划里生成 kind=visit, target=b, window当天已无空闲窗 → 改成「远望」或取消
2 对表查 b 的计划：目标场景是否在窗内、重叠是否 ≥ 20 tick不满足 → 在 ±60 tick 内微调窗口；仍不行 → 降级留信
3 建会话创建 pair session，写 session_participants（a=guest, b=host）场景容量满 → 换场景或降级
4 抢租约按 persona id 排序，一次性写入两段不重叠的 lease任一冲突 → 整个会话不成立，两人各自回到 solo
5 执行按 tick 推进；每 5 tick 允许一次发言，用 attention 决定谁开口模型失败 → 本轮退化为模板，事件标记 degraded
6 收尾写 session.ended；两端各写一条记忆；关系边 ±Δ（单次上限 0.3）崩溃 → 从最后 checkpoint 续跑，事件幂等
关键判断：串门不是「a 给 b 发消息」，而是「a 和 b 同时出现在同一个场景」。所以它必须有共享场景、重叠时间、双向租约三件东西，缺一不可。只发消息不占时间，就退化成聊天记录，不叫串门。
06

模拟流程

一次实时推进里，四个角色的职责要分清：调度器只排时间，执行器只跑会话，生成器只产内容，记忆器只做归档。

一个 tick 里发生什么

  • 调度器：算出当前 tick 应该活跃的会话集合（solo / pair / group），按 user 串行取出。
  • 执行器：对每个会话推进一拍。solo 只更新精力、心情、位置，必要时用模板产一句；pair 额外做「谁开口」的打分。
  • 生成器：只有被判要说话的会话才调用模型；上下文由双方各自的提示板拼成，记忆块各贴各的发言。
  • 记忆器：会话内每 5 tick 抽一次候选；会话结束时强制写一条「这次见面」的摘要，双方视角不同。

会话状态机

状态进入条件退出
planned计划期交集成立到 start_tick → active；租约失败 → cancelled
active租约到手，开始推进到 end_tick → closing；任一方精力耗尽 → early_end
closing会话最后一拍写摘要 + 记忆 → ended
ended正常收尾终态，租约释放
degraded模型失败或超预算仍可继续，但只出模板台词

用户中途打开客户端，不改变会话本身：他只是以「旁观者 / 加入者」身份进入当前场景，成为第三个参与者（trio）。加入不重排日程，只往当前会话追加一条 user.joined 事件；他离开后会话继续。

07

记忆与生成

同一段共处，两个角色各记一份，措辞不同但指向同一个 session。这是「关系」能被两边同时感知的前提。

角色写什么层例子
主人 bK（关系）+ E（情景）「艾尔今晚来庭院找我，说学院考核改到黄昏。」
访客 aK + E「我去庭院找了千鹤，她正在弹琴，没赶我走。」
关系边relation.delta双方 affinity 各 +0.2（单次上限 0.3，防刷）

生成侧仍然遵守上一版的规则：记忆块不进 system，贴在各自最后一条发言之前；pair 会话里两条发言交替出现，但每个人的提示板只装自己的记忆与锚点。模型调用按会话计费，不按角色计费——一次 pair 会话一次调用，避免「两个人各调一次」的账。

防止「串门变成刷好感」：同一天同一对角色最多一次 pair 会话；关系增量按会话计而不是按消息计；连续三天高频串门会触发日程层的冷却（把 visit 意图降权）。
08

失败与补偿

实时系统的难点不在正常路径，在「服务停了两个小时，回来时两人本该在串门」。

场景处理结果
服务离线 / 休眠恢复时从 last_tick 快进到当前；缺失的天补生成计划事件标记 backfilled=true，不调模型
快进跨过一对会话会话按种子执行模板版；仍写 session.ended 与记忆世界连续，但内容降级
执行中崩溃从会话 checkpoint（每 15 tick）续跑；事件幂等键去重不重复写记忆、不重复加好感
租约冲突整个会话取消，两人回 solo；写一条 cancelled 事件宁可不发生，也不让一个人同时在两处
场景容量满访客改到相邻场景等待，超时则留信不硬塞，避免「第五个人站在两人中间」
快进上限：最多补 3 天。超过 3 天按「世界睡了很久」处理：只补日程与状态，不补会话内容，并在世界史里留一条 world.dormant，让角色记忆里出现「那几天很模糊」。
09

关键约束

这八条是硬约束，违反任何一条都会让「同时在场」变成谎话。

C1
单在场

同一角色在同一 tick 只能属于一个会话。用 presence_leases 的时间区间唯一约束保证，不靠应用层自觉。

C2
不跨用户

实时会话的参与者必须属于同一个 user。跨用户串门只能走异步访客协议：申请、限时、只读公开场景、回归写摘要。

C3
计划不可回写

计划一旦开始执行就只能追加 amendment，不能改过去。否则「昨天a去过哪」会被今天的编辑篡改。

C4
幂等

会话执行与事件写入都以 (session_id, tick, actor, seq) 为幂等键；重放不产生第二条记忆、第二次好感。

C5
预算先行

模型调用按会话计、按用户日预算封顶；超预算的会话自动转 degraded，不阻塞世界推进。

C6
可解释

每条自主发言都要能回答「为什么是它、为什么在这」：存 intent_id、attention 分数、session_id。

C7
记忆边界

记忆只写进参与者自己的库；串门不产生「对方私有记忆」的副本，只产生共享会话的公共事件引用。

C8
时间单调

会话与事件的时间戳只增不减；补算与快进也必须落在正确的 tick 上，不允许「现在补一条昨天的消息」却记成今天。

10

对现有实现的影响

不用推翻引擎内核，但要把它从「一个世界」改成「每个用户一个世界」，并新增会话这一层。

现在改成说明
Engine 单例UserWorld + Scheduler调度器持有 N 个 UserWorld，按 user 分片串行
全局 Tick()advanceTo(user, tick)带快进与补偿；不同用户时钟独立
RoomChat 直答SessionRunner + Join用户说话变成加入当前会话，而不是触发一次问答
personas 平铺personas.user_id + 日程表每个角色有自己的 DayPlan 与 intent 序列
无在场概念presence_leases新增表；所有会话创建都过它
memory 按 persona 键(user_id, persona_id)数据不变，作用域加一层；跨用户读直接拒绝

开放问题

  • 用户在线时，是否允许他「暂停」某个角色的一天？倾向：只允许暂停当前会话，不允许暂停整个世界。
  • 跨用户访客协议的频率与边界：是否允许陌生人串门，还是必须互相关注？
  • 日界按用户时区还是服务器时区？现在设计成用户时区，代价是同一台机器上日界不齐。
  • 关系增量的衰减：现在只写了「单次上限」，还没定「多久不联系会回落」。
