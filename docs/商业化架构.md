# OLY Persona 商业化架构与分工

> v0.1 草案 · 2026-11-27
> 本文是**决策记录 + 分工边界**，不是最终定稿。有争议的点写在最后一节，逐轮讨论后改。

---

## 0. 一句话

**服务端是大脑，客户端是显示器。**

所有记忆、人格、推理、第三方调用都在服务端；客户端只负责「把状态画出来」和「把用户输入送上去」。客户端不持有任何权威数据，换设备登录即恢复全部。

---

## 1. 三个决定，以及为什么

### D1 · 服务端用 Go

| 理由 | 说明 |
|---|---|
| 现有代码可直接搬 | 当前 `app.go / chat.go / roam.go / library.go / settings.go` 共 2845 行，业务逻辑（人格七维、记忆打分、快照回滚、漫游状态机）**几乎不用重写**，把 Wails 的绑定层换成 HTTP 层即可 |
| 单二进制部署 | 不留 Python 那种依赖地狱，Docker 镜像 20MB 级 |
| 流式并发 | goroutine 天然适合「一个请求扇出到 N 个角色」的群聊场景 |

**不选 Node**：现有 Go 逻辑要重写一遍，没收益。
**不选 Python**：AI 生态好，但现有代码迁移成本 + 部署运维成本高。真要接本地模型，用 sidecar 单独跑 Python 服务，主服务仍是 Go。

### D2 · 一套 React UI，三端三个壳

这是**整个分工能不能并行**的关键决定。

```
                ┌──────────────────┐
                │  React + TS 前端  │  ← 唯一的一份，UI 组只改这里
                │  （现有 12 个页面）│
                └────────┬─────────┘
                         │ 同一份 build 产物
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   Wails 壳(Go)     Wails 壳(Go)     Capacitor 壳
   Windows          Linux            Android
```

| 端 | 壳 | 现状 |
|---|---|---|
| Windows | Wails v2 | ✅ 已有，继续用 |
| Linux | Wails v2 | ✅ 已有，继续用 |
| Android | Capacitor | 🆕 新建，包一层 WebView |

**为什么不 Flutter**：等于把 12 个页面 + 深紫暗色主题系统全部重写，UI 组的工作量翻三倍，而且桌面端已有的东西全废。
**为什么不 Tauri**：Tauri v2 确实一套代码通吃桌面+移动，但核心是 Rust，你现有 Go 逻辑全得重写。
**为什么 Capacitor 够用**：这个 App 的交互是「聊天 + 卡片列表 + 拖拽」，不是游戏，WebView 完全撑得住。真遇到性能瓶颈（比如长列表、桌宠动画），再针对那一个页面做原生插件。

> ⚠️ 这个决定有代价：Android 上 WebView 的内存占用比原生高，低端机可能吃紧。见第 6 节风险 R3。

### D3 · 服务端持有全部状态

客户端**不存**任何权威数据。本地只保留：

- 最近 200 条消息（离线可读）
- 人设卡片的渲染快照（离线可看）
- 待发送队列（断网时排队，恢复后重发）

**为什么不做本地优先**：本地优先意味着要处理多端冲突合并（CRDT 或 last-write-wins），复杂度是纯服务端的 3 倍，而且这个产品的核心资产是「记忆连续性」——记忆一旦分叉，人设就崩了。商业版必须单点权威。

**代价**：没网就用不了。所以要做「离线只读 + 草稿队列」，见 3.3。

## 2. 服务端架构

### 2.1 分层

```
┌─────────────────────────────────────────────┐
│ 接入层  HTTP/1.1 · WebSocket · TLS           │
├─────────────────────────────────────────────┤
│ 网关   鉴权(JWT) · 限流 · 配额检查 · 路由      │
├─────────────────────────────────────────────┤
│ 业务   人设 · 记忆 · 对话 · 房间 · 社区 · 漫游  │
├─────────────────────────────────────────────┤
│ 编排   LLM 路由 · 流式聚合 · 重试降级 · 计量    │
├─────────────────────────────────────────────┤
│ 存储   Postgres(+pgvector) · Redis · OSS      │
└─────────────────────────────────────────────┘
```

### 2.2 模块清单

| 模块 | 职责 | 从现有代码迁移 |
|---|---|---|
| `auth` | 注册/登录/刷新、设备管理、多端踢下线 | 🆕 |
| `persona` | 七维人格、核心锚点、好感/心情、版本快照 | `app.go` 直接搬 |
| `memory` | 写入、向量召回、重要度衰减、快照回滚 | `app.go` 的 mock 换真 embedding |
| `chat` | 单聊、群聊、剧本房、多人编排 | `chat.go` 搬 |
| `roam` | 漫游场景、精力状态机、定时 tick | `roam.go` 搬，ticker 从进程内改分布式锁 |
| `library` | 技能库、prompt 装配 | `library.go` 搬 |
| `community` | 动态、标签、点赞、评论 | `app.go` 拆出 |
| `provider` | LLM 供应商适配、密钥托管、路由降级 | `settings.go` 的 callAI 扩展 |
| `billing` | token 计量、配额、账单 | 🆕 |
| `push` | 站内推送、系统通知、厂商推送 | 🆕 |

**关键**：`provider` 的 API Key 只在服务端。客户端**永远拿不到**任何上游密钥——这是商业化后最不能出错的一条。

### 2.3 数据模型（Postgres）

```sql
-- 账号
users(id uuid pk, email citext unique, pass_hash, nickname, avatar_url,
      plan text, status text, created_at, deleted_at)
devices(id uuid pk, user_id fk, platform text, push_token text, last_seen_at)

-- 人设与版本
personas(id uuid pk, user_id fk, name, avatar_url, description,
         dims jsonb,          -- 七维：身份/兴趣/观点/经历/成就/社交/其他
         core_anchor jsonb,   -- 不可变的锚点，进化时锁死
         affection numeric, mood text, evo_version int, created_at)
persona_snapshots(id uuid pk, persona_id fk, version int, payload jsonb, created_at)

-- 记忆
memories(id uuid pk, persona_id fk, user_id fk,
         kind text,           -- fact / event / preference / bond
         content text, importance real,
         embedding vector(1024),
         created_at, last_recalled_at,
         decay real default 1.0)
-- 索引：CREATE INDEX ON memories USING hnsw (embedding vector_cosine_ops);

-- 对话
conversations(id uuid pk, user_id fk, kind text, persona_id, room_id, title, created_at)
messages(id uuid pk, conversation_id fk, seq bigint,
         role text, author_id, content text,
         tokens_in int, tokens_out int, created_at)

-- 房间（群聊/剧本）
rooms(id uuid pk, owner_id fk, scene text, state jsonb, created_at)
room_members(room_id, persona_id, joined_at)

-- 计量
usage_records(id uuid pk, user_id fk, kind text, model text,
              tokens_in int, tokens_out int, cost numeric, created_at)
```

**为什么用 pgvector 而不是独立向量库**：记忆总量级是「每用户几千条」，pgvector 的 HNSW 在千万级以内完全够，省掉一套 Milvus/Qdrant 的运维。等单表过亿再拆。

### 2.4 API 契约（对外唯一真相）

全部 `/v1` 前缀，OpenAPI 3.1 定义，客户端 SDK 由它生成。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/auth/register` `/login` `/refresh` | 账号 |
| GET | `/v1/personas` | 列表（含好感/心情，客户端直接渲染） |
| POST | `/v1/personas` | 创建（支持 `raw_text` 由 AI 抽取） |
| GET/PATCH/DELETE | `/v1/personas/{id}` | 详情/更新/删除 |
| POST | `/v1/personas/{id}/chat` | **流式**对话 |
| GET | `/v1/personas/{id}/memories?q=&topk=` | 记忆召回 |
| POST | `/v1/personas/{id}/rollback` | 回退到某个 snapshot |
| GET | `/v1/conversations/{id}/messages?after_seq=` | 增量拉消息 |
| POST | `/v1/rooms/{id}/say` | 房间插话，**流式** |
| WS | `/v1/stream` | 长连接：聊天增量 + 状态变更 + 漫游推送 |

**每个响应都带 `server_time` 和 `seq`**，客户端靠它做增量同步和乱序丢弃。

### 2.5 流式协议

聊天不能等整段生成完再返回，必须边生成边推。

```
建立：GET /v1/personas/{id}/chat  (Accept: text/event-stream)
     或 WS /v1/stream 后发 {"t":"chat.start","persona_id":"..."}

帧类型：
{"t":"delta",  "msg_id":"m1", "d":"她抬"}          ← 增量文本
{"t":"state",  "persona_id":"p1", "d":{"affection":6.2,"mood":"happy"}}  ← 状态变更
{"t":"meta",   "msg_id":"m1", "d":{"tokens":87}}   ← 计量
{"t":"done",   "msg_id":"m1"}
{"t":"error",  "code":"quota_exceeded","msg":"..."}
```

**为什么 WS 优先、SSE 兜底**：群聊里多个角色同时说话，需要服务端主动推；SSE 只能单向上行靠另一次请求。但 WebView 环境 SSE 兼容性更好，所以两条都实现，客户端自动选。

### 2.6 多租户与计费

| 层 | 做法 |
|---|---|
| 鉴权 | JWT access(15min) + refresh(30d)，refresh 存 Redis 可吊销 |
| 隔离 | **所有查询强制带 `user_id`**，用 Postgres RLS 兜底，防越权 |
| 配额 | Redis 计数器，按天/按月；超限返回 `quota_exceeded` |
| 计量 | 每次 LLM 调用写 `usage_records`，异步聚合账单 |
| 密钥 | 上游 Key 存 KMS/环境变量，服务端统一托管，按用户分配模型档位 |

## 3. 客户端架构

### 3.1 三端形态

| 端 | 壳 | 打包 | 交付物 |
|---|---|---|---|
| Windows | Wails v2（Go） | `build.ps1` → `.exe` | `oly-persona.exe` |
| Linux | Wails v2（Go） | `build.sh linux` | AppImage / deb |
| Android | Capacitor 7（WebView） | Gradle → `.apk` | `oly-persona.apk` |

三端共用 `frontend/` 同一份源码，只在壳层做差异：

```
frontend/                 ← 唯一 UI 源码，三端共享
platform/
  desktop/                ← Wails 的 main.go 与绑定（Windows + Linux）
  android/                ← Capacitor 工程（android/ + capacitor.config.ts）
```

### 3.2 客户端只做四件事

1. **渲染**服务端下发的状态
2. **上传**用户输入
3. **订阅**流式帧并增量更新
4. **缓存**最近数据供离线只读

不做：记忆打分、人格演化、prompt 拼装、调用 LLM。这些全在服务端。

### 3.3 断线重连与离线

```
发送消息 → 入本地 outbox（带 client_msg_id）
        → POST/WS 上行
        → 服务端回 ack（含 seq）
        → 从 outbox 移除
断线重连 → 带 last_seq 重连 → 服务端补发 seq > last_seq 的帧
```

**幂等**：`client_msg_id` 是客户端生成的 UUID，服务端按它去重。这样重发不会产生重复消息。

## 4. 四条工作线（分工）

### 4.1 边界表

| 线 | 负责目录 | 交付物 | 不动什么 |
|---|---|---|---|
| **A 服务端** | `server/**`、`api/openapi.yaml` | Go 服务、DB 迁移、Docker、契约 | 不碰 `frontend/` |
| **B Windows 端** | `platform/desktop/**`、`build.ps1` | `.exe`、安装包、自动更新 | 不改 `frontend/src/` 的业务逻辑 |
| **C Android + Linux 端** | `platform/android/**`、`build.sh` | `.apk`、AppImage、推送接入 | 同上 |
| **D UI 调优** | `frontend/src/**` | 视觉、交互、动效、主题 | **不改 API 调用契约** |

### 4.2 让四条线并行的三个硬约束

1. **契约先冻**
   `api/openapi.yaml` 在 M0 结束前定稿。之后要改字段，必须走「改契约 → 通知 A/B/C/D 四方 → 同时更新」的流程，不许某一端私自加字段。

2. **Mock 服务先行**
   A 组在契约冻结当天产出一个 Mock Server（返回假数据但符合契约）。B/C/D 从第一天就对着 Mock 开发，不等真接口。**这是四条线能真正并行的唯一办法。**

3. **生成式 SDK，不手写请求**
   `openapi-typescript` 生成 `frontend/src/api/schema.d.ts`，各端只用生成的类型。手写 `fetch` 是 bug 之源。

### 4.3 协作节奏

| 频率 | 事项 |
|---|---|
| 每天 | 各自跑通 Mock + 自己的模块，不阻塞别人 |
| 每周一 | 契约评审：只讨论「要改什么字段」，不改别的 |
| 每周五 | 集成：真服务端 + 真客户端联调，修契约不一致 |
| 里程碑 | 见第 5 节，每个里程碑出一次可安装包 |

### 4.4 依赖方向（谁等谁）

```
契约(openapi.yaml)
   ├─→ A 服务端（真实现）
   ├─→ B/C 壳（只依赖契约，不依赖 A 的实现）
   └─→ D UI（只依赖契约，用 Mock）
```

**A 不阻塞任何人**，因为 B/C/D 都有 Mock。反过来 D 改 UI 也不阻塞 A，因为契约没变。

## 5. 里程碑

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **M0 契约** | `openapi.yaml` 定稿 + Mock Server | Postman/前端能跑通全部接口的假数据 |
| **M1 服务端单机** | A 组真实现，Postgres 跑起来 | 一个真人账号能建人设、聊天、召回记忆 |
| **M2 桌面可用** | Windows/Linux 接真服务端 | `.exe` 双击能登录、聊天、看记忆 |
| **M3 移动端** | Android 出包 | `.apk` 装到真机，聊天能用 |
| **M4 商业化** | 计费、配额、风控、推送 | 能跑通「免费额度用完 → 提示升级」 |
| **M5 运营** | 后台管理、数据分析、灰度 | 能看日活、能封号、能发公告 |

## 6. 风险与待决

### 已识别的风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | **Android 推送在国内不可用** | 桌宠/漫游通知推不出去 | FCM 走不通就接厂商推送（小米/华为/OPPO/vivo）或自建长连接；这块工作量要单列 |
| R2 | **LLM 成本失控** | 商业化的命门 | 服务端强制配额 + 按档位限模型 + 缓存相同 prompt |
| R3 | Android WebView 内存 | 低端机卡顿/被杀 | 长列表虚拟滚动；桌宠动画在移动端降级为静态 |
| R4 | **生成式 AI 备案** | 国内上线合规硬门槛 | 提前准备算法备案与内容安全审核接口 |
| R5 | 记忆隐私 | 全量上云，泄露即事故 | 字段级加密 + 用户可导出/删除 + 审计日志 |
| R6 | 单人开发四条线 | 实际上不可能并行 | 见下方 Q1 |

### 需要你拍板的问题

**Q1 · 这四条线现在是几个人？**
如果是你一个人 + 我，那「四条线并行」是假的，真实做法是**串行但解耦**：先把契约和服务端做扎实，桌面端跟着改，Android 最后。分工表要按「阶段」而不是「并行组」来排。

**Q2 · 记忆要不要对用户可导出/可私有化部署？**
商业版如果卖给企业客户，通常要求「数据不出境/可私有化」。这会倒逼服务端做成可单机部署的形态，架构上要预留。

**Q3 · 免费额度怎么定？**
按天给 token，还是按「对话轮数」？前者对用户透明但对成本不可控，后者好算账但限制感强。

**Q4 · 群聊多角色同时说话，算力怎么控？**
一个房间 5 个角色，一轮可能触发 5 次 LLM 调用。是每轮都让所有角色说话，还是按「说话意愿」采样？
