## 一、一次性准备（只做一次）

### 1.1 生成密钥

一把钥匙 = 一对文件。`.pub` 结尾的是公钥（可以随便给人），不带后缀的是私钥（**永远不离开本机**）。

```bash
ssh-keygen -t ed25519 -C "oly-persona-deploy" -f ~/.ssh/oly_deploy -N ""
```

- `-t ed25519`：现在推荐的算法，比 RSA 短得多也更快
- `-C`：备注，会写进公钥末尾，方便以后认领
- `-f`：文件名，不写的话默认 `id_ed25519`
- `-N ""`：不设密码。设了密码每次 push 都要输，自动化场景建议不设

生成完会得到两个文件：

```
~/.ssh/oly_deploy       ← 私钥，别动它
~/.ssh/oly_deploy.pub   ← 公钥，贴到 GitHub
```

> **本机实际情况**：这个密钥对的路径是 `/mnt/project/AI-All/OLY/.ssh/oly_deploy`，
> 指纹 `SHA256:BcgkC/17jhaUWK6uwO2Bl50tS2iNMQNjfAbNwBOudfQ`，已在 GitHub 上以
> 「ALL-deep」为标题添加，权限为**读/写**。
> ⚠️ 工作区是 fuse 挂载，`chmod` 在这上面**不生效**（改完还是 755，ssh 会拒绝使用）。
> 所以私钥必须拷到 `~/.ssh/` 再用，那里才能改成 600。

### 1.2 把公钥贴到 GitHub

**用途不同，加的位置完全不同，别加错：**

| 你想干什么 | 加在哪 | 中文界面的名字 | 作用范围 |
|---|---|---|---|
| 仓库里的机器/成员推代码 | 仓库 → Settings → Deploy keys | **部署密钥** | 只对**这一个仓库**有效 |
| 你本人所有仓库都能推 | 个人 Settings → SSH and GPG keys | SSH 密钥 | 你名下**全部仓库** |
| 脚本/CI 调 GitHub API | 个人 Settings → Developer settings → Token | 个人访问令牌 | 按勾选的权限 |

本项目用的是**第一种**（一把钥匙只管这一个仓库，泄露了也炸不到别处）。

添加步骤：

1. 打开仓库 → `Settings` → 左侧「安全与质量」分组 → 「高级安全」→ **部署密钥**
   > 中文界面把 Deploy keys 机翻成了"部署密钥"，搜"key"搜不到。
2. 点 `Add deploy key`
3. Title 随便写（建议和密钥 `-C` 备注一致，方便对应）
4. Key 里粘贴 `cat ~/.ssh/oly_deploy.pub` 的**全部内容**（`ssh-ed25519` 开头那一整行）
5. **要推代码就勾上 `Allow write access`**（默认是不勾的，不勾只能拉取）
6. 保存后核对指纹：页面显示的 `SHA256:...` 要和下面命令输出一致

```bash
ssh-keygen -lf ~/.ssh/oly_deploy.pub
```

### 1.3 配 ssh 别名（这一步不做，后面必失败）

**Deploy key 不会自动生效。** 你 `git push` 到 `github.com` 的时候，ssh 只会去找
`~/.ssh/id_rsa`、`id_ed25519` 这类**默认文件名**，你的钥匙叫 `oly_deploy`，
它根本不会被用到，结果就是 `Permission denied (publickey)`。

解决办法是给它起个 GitHub 专用的别名：

```bash
cat >> ~/.ssh/config <<'EOF'

Host github-oly
  HostName github.com
  User git
  IdentityFile ~/.ssh/oly_deploy
  IdentitiesOnly yes
EOF

chmod 600 ~/.ssh/config
```

`IdentitiesOnly yes` 是关键——不加的话 ssh 还是会挨个试默认钥匙，试错次数多了会被 GitHub 拒。

**remote 地址必须用别名，不能用 github.com：**

```bash
# ✅ 对：主机名是别名，ssh 才知道用哪把钥匙
git@github-oly:用户名/仓库名.git

# ❌ 错：主机名是 github.com，会去试默认钥匙然后失败
git@github.com:用户名/仓库名.git
```

### 1.4 配 remote

```bash
cd /mnt/project/AI-All/OLY/oly-persona

# 已经配过就先改，别 add 两次（会报 remote origin already exists）
git remote remove origin 2>/dev/null

git remote add origin git@github-oly:Genhutao/仓库名.git
git remote -v          # 确认地址对
```

### 1.5 验证

```bash
ssh -T git@github-oly
```

- 成功会看到：`Hi Genhutao/仓库名! You've successfully authenticated, but GitHub does not provide shell access.`
  注意前缀是 **`用户名/仓库名`** 而不是单纯的用户名——这正是 Deploy key 的特征（它认的是仓库，不是人）
- 失败会看到：`Permission denied (publickey)` → 回 1.3 检查别名和 `IdentitiesOnly`

## 二、日常提交流程（每次改完代码）

```bash
cd /mnt/project/AI-All/OLY/oly-persona

# 1. 看现在是什么状态（哪些改了、哪些是新文件）
git status

# 2. 看具体改了什么（提交前一定过一眼，防止把调试代码、密钥、临时文件带进去）
git diff                  # 还没 add 的改动
git diff --staged         # 已经 add 的改动

# 3. 加入暂存区
git add -A                # 全部
git add app.go chat.go    # 只加指定文件（更推荐，便于拆成多个提交）

# 4. 提交
git commit -m "feat(chat): 群聊支持 @ 指定角色插话"

# 5. 推上去
git push
```

### 提交前必做的三道自检

```bash
# ① 有没有把密钥/令牌带进去（结果为空才安全）
git diff --staged | grep -nE 'sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{20,}|BEGIN (RSA|OPENSSH) PRIVATE KEY'

# ② 有没有把不该进的目录带进去（应该只列出源码和文档）
git diff --staged --name-only

# ③ 有没有把编译产物带进去（bin/、build/、node_modules/ 都不该出现）
git diff --staged --name-only | grep -E '^(bin|build)/|node_modules|\.exe$'
```

这三条如果有一条出问题，先 `git restore --staged <文件>` 撤出暂存区，再补 `.gitignore`。

## 三、提交信息怎么写

格式统一用 Conventional Commits：

```
<类型>(<范围>): <一句话说明>

<可选：为什么要改，改之前是什么样，改之后是什么样>
```

### 类型对照表

| 类型 | 什么时候用 | 例子 |
|---|---|---|
| `feat` | 新增功能 | `feat(memory): 记忆召回加入时效衰减` |
| `fix` | 修 bug | `fix(chat): 修历史消息过多时气泡错位` |
| `refactor` | 重构，行为不变 | `refactor(roam): 精力状态机拆成独立文件` |
| `style` | 只改格式/空白/命名 | `style: 统一缩进为 2 空格` |
| `docs` | 只改文档 | `docs: 补代码提交指南` |
| `test` | 加/改测试 | `test(persona): 补快照回滚用例` |
| `chore` | 杂活（依赖、脚本、配置） | `chore: 升级 wails 到 v2.9.1` |
| `perf` | 性能优化 | `perf(memory): 向量检索改为批量计算` |
| `build` | 构建配置 | `build: Windows 打包加 -H windowsgui` |

**范围**填模块名，从本项目的实际结构里取：`persona` `chat` `roam` `memory` `library` `github` `community` `settings` `ui` `pet` `build`。

### 好与坏

```
✅ feat(persona): 支持导入整本书由 AI 抽取人设
✅ fix(chat): 修切换角色后上一条消息气泡残留
✅ chore: 把 bin/ 和 frontend/dist/ 加进 .gitignore

❌ 更新                （更新了什么？）
❌ fix bug             （什么 bug？）
❌ 改了一下             （改了哪、为什么？）
❌ 11月27日提交         （时间 git 自己会记，不用你写）
```

### 什么时候需要写正文

改动**看不出理由**的时候。比如：

```
perf(memory): 向量打分改为一次算完

原来每条记忆都单独调一次 cosineSim，200 条记忆要扫 200 遍。
改成先把查询向量和所有记忆点积一遍，耗时从 40ms 降到 3ms。
没改成更复杂的索引结构，是因为 demo 阶段记忆量不会超过 1000 条，
引入 HNSW 不划算。
```

**"为什么没选另一个方案"比"做了什么"更值钱**——半年后你会感谢自己写了这句。

## 四、分支与 PR

### 什么时候直接推 main，什么时候开分支

| 情况 | 做法 |
|---|---|
| 只有你一个人写，改的是文档/小修 | 直接推 `main` |
| 功能开发、大重构 | 开分支，做完合并 |
| 别人给你提代码 | 走 PR（见第五节） |

### 分支命名

```bash
git checkout -b feat/memory-decay      # 功能
git checkout -b fix/chat-bubble        # 修 bug
git checkout -b chore/upgrade-wails    # 杂活
```

### 开发完合并回 main

```bash
git checkout main
git pull                     # 先把别人的改动拉下来
git merge feat/memory-decay  # 或者 git rebase，看你团队习惯
git push
```

合并后可以删掉分支：`git branch -d feat/memory-decay`

### 后悔药

```bash
git log --oneline            # 看提交历史，拿到 commit id
git revert <commit-id>       # 推荐：生成一个"反向提交"抵消掉，历史保留
git reset --soft HEAD~1      # 撤销最后一次提交，但改动还留在工作区
```

> **已经在 GitHub 上的提交别用 `reset` + 强推**，会让别人的本地历史对不上。
> 线上用 `revert`，本地还没推的用 `reset`。

## 五、让别人能给你提交代码

三种方式，按需要的信任程度递增：

### 方式 A：加 Collaborator（最常用）

对方用**自己的** GitHub 账号推代码，权限跟着账号走。

1. 仓库 → `Settings` → 「访问」分组 → **「合作者」**（Collaborators）
2. `Add people` → 输入对方用户名或邮箱 → 选权限（`Read` / `Triage` / `Write` / `Maintain` / `Admin`）
3. 对方接受邀请邮件后就能 `git clone` 并推送

**优点**：撤销简单，直接删掉这一个 collaborator 就完事，不影响别人。
**注意**：`Write` 权限能直接推 main，也能删分支。不放心就只给 `Read`，让他们走方式 B。

### 方式 B：只读 + Fork + PR（最安全）

对方 fork 一份到自己账号 → 改完提 PR → 你审完才合。

1. 对方：仓库页右上角 `Fork` → 在自己那份上改 → `Compare & pull request`
2. 你：在 `Pull requests` 里看 diff、留评论、`Merge pull request`

**不需要给对方任何权限**，代码进不进来完全由你决定。适合开源协作和不熟的贡献者。

### 方式 C：Deploy Key（密钥形式，本项目用的）

不用给对方 GitHub 账号，直接把一把 SSH 钥匙挂到仓库上。

1. 对方在**自己机器**上生成密钥（**每台机器一把，不要共用一把**）
2. 把 `.pub` 内容给你
3. 你：仓库 → Settings → 部署密钥 → `Add deploy key` → 想让他推就勾 `Allow write access`

**优点**：适合脚本、CI、服务器这类没有"人"的场景；泄露了只影响这一个仓库。
**限制**：

- 一把公钥**只能挂一个仓库**（同一把钥匙挂第二个仓库会报 `Key is already in use`）。
  想给多个仓库用，就生成多把，或者改用机器账号（Machine User）。
- 一个仓库**可以挂多把** deploy key，够用。
- 用 deploy key 推的提交，在 GitHub 上显示的作者是钥匙的名字，不关联到具体人的头像。

## 六、本项目专属注意事项

### 6.1 哪些不进仓库（已在 `.gitignore` 里配好）

| 路径 | 为什么 |
|---|---|
| `bin/`、`build/bin/`、`*.exe` | 编译产物，10MB 级别，而且每次构建都变 |
| `frontend/node_modules/` | 依赖，`pnpm install` 就能还原 |
| `frontend/dist/` | 前端构建产物，`pnpm build` 生成 |
| `.gocache/` `.gomodcache/` `.gopath/` `.pnpm-store/` | 构建缓存 |
| `.ssh/` `*.pem` `*.key` `.env` | **密钥，进仓库等于把钥匙挂在门上** |
| `*.log` `.DS_Store` | 噪音 |

如果确实需要传二进制（比如给不会编译的人直接运行的 exe），**不要提交进 git**，
而是用 GitHub 的 `Releases` 功能上传附件——不占仓库体积，也不进版本历史。

### 6.2 本次首次提交包含什么

- **64 个文件**，`.git` 体积 **4.3 MB**
- 提交 `f3878cb`：`feat: OLY Persona — 人设扮演 / 长期记忆 / 剧情演绎 / OC 社区`
- 工作区干净，`bin/`、`build/`、`frontend/dist/`、`frontend/node_modules/` 均已正确忽略

### 6.3 换行符

仓库里统一存 **LF**。Windows 上检出 `.ps1` / `.bat` / `.cmd` 时自动转 **CRLF**，
其余文件保持 LF。这是 `.gitattributes` 在做的事，**不要手动去改**。

如果改完代码 `git status` 显示一大片莫名其妙的"整个文件都改了"，多半是换行符被
编辑器改掉了：

```bash
git diff --stat             # 确认是不是整个文件都标红
git restore <文件>          # 撤掉，用编辑器重新改
```

### 6.4 构建命令（提交前先确认能编过）

```bash
./build.sh              # 当前平台
./build.sh linux        # linux/amd64
./build.sh windows      # windows/amd64 → bin/oly-persona.exe

# Windows 上：
pwsh -File .\build.ps1
pwsh -File .\build.ps1 -Target linux
```

本地开发热重载用 `wails dev`，但它**不进提交**——它只改内存里的东西，不产生需要入库的文件。

`go test ./...` 能过再提交，`app_test.go` 里有单元测试。

### 6.5 设置里填的 API Key / GitHub Token

这些**存在用户配置目录**（`settings.go` 负责落盘到用户配置目录），不在仓库里，
也不会被提交。但**千万别为了调试把它们硬编码进源码**——一旦提交，就算后来删掉，
历史记录里还躺着，得重写历史才能清掉。用环境变量或设置界面。

## 七、常见错误速查

| 报错 / 现象 | 原因 | 怎么修 |
|---|---|---|
| `Permission denied (publickey)` | ssh 没用到那把钥匙 | 检查 remote 主机名是不是 `github-oly`；`~/.ssh/config` 里有没有 `IdentitiesOnly yes` |
| `Permission denied (publickey)` 但 config 都对 | 私钥权限太宽，ssh 拒绝使用 | `chmod 600 ~/.ssh/oly_deploy`（fuse 挂载改不动就换个位置） |
| `Bad owner or permissions on /etc/ssh/ssh_config.d/...` | 系统级 ssh 配置文件权限不对 | 这是环境问题，不是你的仓库问题；`chmod 644` 该文件，或用 `ssh -F ~/.ssh/config` 绕开 |
| `Key is already in use` | 同一把公钥想挂第二个仓库 | 新生成一把，用 `ssh-keygen -f ~/.ssh/另一把` |
| `remote origin already exists` | remote 配过了 | `git remote set-url origin <新地址>` 或先 `git remote remove origin` |
| `Updates were rejected because the remote contains work...` | GitHub 那边有你这没有的提交（比如建仓库时勾了 README） | `git pull --rebase origin main` 再推 |
| `fatal: refusing to merge unrelated histories` | 本地和远端是两段互不相干的提交历史 | `git pull origin main --allow-unrelated-histories` |
| `src refspec main does not match any` | 本地还没有 main 分支（没提交过） | 先 `git add -A && git commit -m "..."` |
| `LF will be replaced by CRLF` 警告 | 正常提示，不是错误 | 忽略 |
| 提交了整个 `node_modules` | `.gitignore` 没生效或文件早被跟踪 | `git rm -r --cached frontend/node_modules && git commit` |
| 误提交了密钥 | —— | **立刻去 GitHub 撤销/删除那把钥匙**，再 `git rm --cached` 并提交；光删文件不够，历史里还有 |
| `git push` 卡住不动 | 网络问题或没配代理 | `GIT_CURL_VERBOSE=1 git push` 看卡在哪；ssh 方式不走 http 代理 |
